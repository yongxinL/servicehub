# Woodpecker CI — ServiceHub

> Container-native CI/CD: a server that schedules pipelines and an agent that executes every step in an ephemeral Docker container.

## Overview

[Woodpecker CI](https://woodpecker-ci.org/) runs pipelines for repositories hosted on [Forgejo](../forgejo/README.md). It is defined in [`compose/devop.yml`](../../compose/devop.yml) and built from [`shared/woodpecker/server/Dockerfile`](server/Dockerfile) and [`shared/woodpecker/agent/Dockerfile`](agent/Dockerfile) (`FROM woodpeckerci/woodpecker-{server,agent}:${IMAGE_TAG}`).

## Components

| Service | Role |
|---|---|
| `devopbldinit` | One-shot: `chown -R 1000:1000` on the Forgejo and Woodpecker data directories before the server starts |
| `devopbldserv` | Web UI, API, pipeline scheduler and gRPC endpoint; talks to Forgejo over OAuth2 + webhooks |
| `devopbldexec` | Agent: pulls jobs over gRPC and runs each step as a Docker container on the host |

Startup order: `devopbldinit` completes → `devopbldserv` starts (once Forgejo is healthy) → `devopbldexec` connects to the server's gRPC port.

## Service details

| Detail | Value |
|---|---|
| Server URL | `https://${GITBLD_DOMAIN}` |
| Server ports | 8000 (HTTP UI/API), 9000 (gRPC for agents — internal) |
| Server database | SQLite (`${APPS_DATA}/devops/buildserv/woodpecker.sqlite`) |
| Server data | `${APPS_DATA}/devops/buildserv` (mounted at `/var/lib/woodpecker`) |
| Agent backend | `docker` |
| Agent data | `${APPS_DATA}/devops/buildexec` (mounted at `/etc/woodpecker`) |
| Agent network | joins `${GITBLD_NETWORK}` so pipeline containers can reach stack services |
| Image tag | `GITBLD_VTAG` (default `v3`) |
| Registration | Closed (`WOODPECKER_OPEN=false`); users come from Forgejo OAuth |

## Configuration

Set in `.env` (see [`env.example`](../../env.example)):

| Variable | Description |
|---|---|
| `GITBLD_DOMAIN` | Woodpecker hostname (e.g. `run.example.com`) |
| `GITBLD_VTAG` | Woodpecker image tag passed to the Dockerfiles as `IMAGE_TAG` |
| `GITBLD_OA_CLIENT` | Forgejo OAuth2 client ID (mandatory) |
| `GITBLD_OA_SECRET` | Forgejo OAuth2 client secret (mandatory) |
| `GITBLD_AGN_SECRET` | Shared secret authenticating the agent to the server (`openssl rand -hex 32`) |
| `GITBLD_GRPC_SECRET` | Signing secret for gRPC JWTs (`openssl rand -hex 32`) |
| `GITBLD_ADMUSR` | Comma-separated Forgejo usernames granted Woodpecker admin |
| `GITBLD_NETWORK` | Docker network pipeline containers join (`servicehub_subnet`) |
| `GITREPO_DOMAIN` | Public Forgejo host used to build browser OAuth URLs |
| `APPS_DATA` / `TIME_ZONE` | Host data path / container timezone |

`GITBLD_AGN_SECRET` and `GITBLD_GRPC_SECRET` are auto-generated by `scripts/setup.sh`.

### Forgejo reachability

The server uses two different Forgejo URLs:

| Variable | Value | Used for |
|---|---|---|
| `WOODPECKER_FORGEJO_URL` | `http://devopgitserv:3000` | Server-to-server API calls over the stack network (no TLS) |
| `WOODPECKER_EXPERT_FORGE_OAUTH_HOST` | `https://${GITREPO_DOMAIN}` | Building the public OAuth authorize/redirect URLs that browsers navigate to |

## Data & persistence

| Container path | Host path | Purpose |
|---|---|---|
| `/var/lib/woodpecker` (server) | `${APPS_DATA}/devops/buildserv` | SQLite database |
| `/etc/woodpecker` (agent) | `${APPS_DATA}/devops/buildexec` | Agent registration/config (`agent.conf`) |

`devopbldinit` runs as root and normalises ownership to UID/GID `1000` on every boot.

## Setup (first boot)

1. Make sure Forgejo is running and you have an admin account on it.
2. In Forgejo, create an OAuth2 application:

   **Site Administration → Applications → Create**
   - Name: `Woodpecker`
   - Redirect URI: `https://${GITBLD_DOMAIN}/authorize` (must match `WOODPECKER_HOST`)

3. Copy the generated client ID and secret into `.env` as `GITBLD_OA_CLIENT` / `GITBLD_OA_SECRET`, and set `GITBLD_ADMUSR` to your Forgejo username.
4. Start the stack:

    ```bash
    docker compose up -d devopbldserv devopbldexec
    ```

5. Open `https://${GITBLD_DOMAIN}` and log in with your Forgejo account. Activate the repositories you want to build and add a `.woodpecker.yml` pipeline definition.

## Operations

```bash
# Start / restart the server and agent
docker compose up -d devopbldserv devopbldexec

# Follow logs
docker compose logs -f devopbldserv
docker compose logs -f devopbldexec

# Rebuild after a Dockerfile change
docker compose up -d --build devopbldserv devopbldexec
```

### Reset (destructive)

```bash
docker compose down devopbldserv devopbldexec
rm -rf ${APPS_DATA}/devops/buildserv/* ${APPS_DATA}/devops/buildexec/*
docker compose up -d devopbldserv devopbldexec
```

> This deletes the SQLite database (all users, repos and pipeline history) and the agent registration.

## Notes & troubleshooting

- The agent mounts the Docker socket and must run rootful (the default for the docker backend); it launches pipeline containers on the host daemon.
- Pipeline containers join `servicehub_subnet`, so they can resolve stack services by name. Clones, however, use the public URL reported by Forgejo (`https://${GITREPO_DOMAIN}`) — on staging with a self-signed certificate, add the CA to the clone step's trust store or run against production.
- `WOODPECKER_OPEN=false` disables self-service registration. Only users listed in `GITBLD_ADMUSR` can log in initially; add further users with the Woodpecker CLI (`woodpecker-cli user add`).
- If the agent cannot connect, verify `GITBLD_AGN_SECRET` is identical on the server and agent, and that the server is healthy.
